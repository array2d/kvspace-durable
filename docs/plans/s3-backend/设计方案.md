# s3:// 后端 · 设计方案

> 日期：2026-09-26
> 目标：给 kvspace-durable 增加 `s3://` 后端，成为 moechat 的存储底座
> 本文是**设计方案**，确认后才写代码。

---

## 一、为什么加得很自然

现有结构已经把这件事铺好了：

```
conn(dsn)                      ← src/conn.rs，按 scheme 分发
  ├─ "redis" → Backend::new(redis::connect(addr))
  └─ "fs"    → fs::connect(addr)

Backend<S: KVStore>            ← src/backend.rs，KVSpace 逻辑，参数化于 store
KVStore trait                  ← src/store.rs，6 个必实现 + 4 个有默认
```

**加 S3 = 给 `KVStore` 写一个实现 + 在 `conn()` 里加一条分支。** `backend.rs` 一行不用动。

`Cargo.toml` 的 description 里本来就写着「后端 redis/fs/s3」——这从来就在计划里。

## 二、三个必须先定的问题

这三个不定，代码没法写。

### 2.1 HTTPS：零依赖做不做得到？

**做不到。** `std` 没有 TLS。redis 后端能用 `TcpStream` 手写 RESP，是因为 Redis 走明文 TCP；
S3 必须 HTTPS，而 TLS 不是能绕过去的东西。

四条路：

| 方案 | 代价 | 判断 |
| --- | --- | --- |
| **A. 加 `ureq`（rustls）** | 引入约 30–40 个传递依赖；二进制变大；构建变慢 | **推荐**。成熟、阻塞式、API 简单，和现有同步风格一致 |
| B. 加 `rustls` + 手写 HTTP/1.1 | 依赖少一些，但要自己写 chunked / 连接复用 / 重定向，是几百行容易写错的代码 | 不划算 |
| C. 用明文 `http://` | 零依赖，腾讯 COS 支持 80 端口 | **不可接受**。签名和载荷全在明文里，公网链路上等于不设防 |
| D. `Command::new("curl")` | 零 Rust 依赖 | **不可接受**。库带 C ABI，被嵌进 kvlang，靠起子进程做每次 IO 是荒谬的 |

**这是本仓库的第一个依赖，所以它是一次政策决定，不只是技术选择。**
零依赖到目前为止是真的（`[dependencies]` 是空的）。加 `ureq` 之后就不是了。

> **待确认 1**：接受引入 `ureq` 吗？还是宁可要 B 那种「少依赖但多代码」？

### 2.2 凭据怎么传：**放进 DSN，但必须先做脱敏**

**决定（需求方 2026-09-26）**：不引入 `AWS_*` 那套环境变量，改为**凭据进 DSN**，
并用一个统一的 `KVSPACE` 环境变量装整串 DSN。

```
KVSPACE=s3://AKID…:SECRET…@moechat-test-1252231640/moechat/?endpoint=cos.ap-beijing.myqcloud.com&region=ap-beijing

conn("")          → 读 $KVSPACE
conn("s3://…")    → 用给的那一串
```

理由：本仓库的既有设计就是**一切配置都在 DSN 里**（`redis://host:port`、`fs:///path`）。
凭据走另一套机制会变成第二个真相源。`scheme://user:pass@host` 也是 URI 的通行写法
（redis 的密码将来同样可以这么带）。

**但有一个前置条件，不做就不能这么干。**

DSN 会进日志、panic 消息、错误信息。而**现在就有一处会原样打印 DSN**：

```rust
// src/conn.rs:17
_ => panic!("kvspace: unknown scheme {:?} in dsn {:?}", scheme, dsn),
```

一旦凭据进 DSN，这一行就会把密钥写进日志。

**所以本期必须同时做**：

1. 新增 `redact_dsn(&str) -> String`，把 `scheme://user:pass@` 里的 **user 与 pass 换成 `***`**，
   其余原样保留（host / path / query 不是秘密，保留才便于排查）
2. **所有**提到 DSN 的 panic / 日志一律走它。目前只有 `conn.rs:17` 一处，
   但新增的 S3 错误路径也要遵守
3. `redis/store.rs:26` 打印的是 `addr`，将来 redis 支持 `redis://:pass@host` 时同样要走脱敏

**待确认 2**：`conn("")` 读 `$KVSPACE` 这个兜底要不要做？还是只接受显式传入的 DSN？
（做的话，空串 DSN 就有了「从环境读」的含义，与「参数为空 = 用默认」的直觉略有出入。）

### 2.3 `set_part`：S3 对象不可变，没有按偏移写

| 方案 | 说明 |
| --- | --- |
| **复用 trait 默认实现**（整读 → 改 → 整写） | 零额外代码，语义正确。**代价是 O(对象大小) 每次** |
| S3 Multipart Upload | 只能在 5 MB 边界切分，还要重传整个对象，对小写入更糟 |

**推荐先用默认实现**，理由是 KVSpace 会大量走 `set_part` 改索引（`encode_index_grow` 那条路径），
每次一个 HTTP 往返加一次全量重写，可能很慢——**但这是「可能」，没有实测**。
先按最简单的做对，拿真实负载量一次，再决定要不要优化。不在没有数据的情况下先写缓存层。

> **待确认 3**：接受「先整读整写、按需再优化」吗？

## 三、DSN 形态

```
s3://<AccessKeyId>:<AccessKeySecret>@<bucket>/<prefix>?endpoint=<host>&region=<region>

例：
s3://AKID…:SECRET…@moechat-test-1252231640/moechat/?endpoint=cos.ap-beijing.myqcloud.com&region=ap-beijing
```

| 部分 | 必填 | 说明 |
| --- | --- | --- |
| userinfo | ✅ | AccessKeyId : AccessKeySecret。按 URI 通行写法放这里 |
| bucket | ✅ | |
| prefix | ✅ | 见下 |
| `endpoint` | ✅ | 腾讯 COS 的接入点，如 `cos.ap-beijing.myqcloud.com` |
| `region` | ✅ | 如 `ap-beijing`。SigV4 签名要用 |

**前缀不是可选的礼貌，是隔离手段。** 一个桶要能装多个 kvspace（开发/测试/生产、或多个主体）。
`flush()` 只清自己的前缀，见 §六。**所以前缀强制必填**，不给「桶根」这种配法。

DSN 解析：`conn.rs` 现在只做 `find("://")` 切 scheme，不够用了。
新增一个小的 URI 解析（scheme / userinfo / host / path / query），
query 里 `&` 切、`=` 分，值做百分号解码——**包括 userinfo，因为在 URI 里
secret 常含 `/` `+` `=` 这类字符，必须百分号编码**。这一点容易漏。

**解析失败一律 panic 并说清缺哪一段**，不做默认值兜底——
凭据配错时给出「用了一个空 secret 去签名」这种结果，比直接崩难查得多。

## 四、key 映射

**KVSpace key → S3 object key = `<前缀>` + `<原 key>`，不做任何编码。**

先确认这可行：KVSpace 的 key 里会出现

| 字符 | 出处 | S3 对象名允许吗 |
| --- | --- | --- |
| `/` | `PATH_SEP`，也是 `DIR_INDEX_SUF` | ✅ |
| `·` U+00B7 | `OBJ_SEP` 成员分隔符 | ✅ |
| `‥` U+2025 | `RUNTIME_MEMBER_SEP` | ✅ |
| `…` U+2026 | `EXT_INDEX_HEAD` | ✅ |
| 任意成员名 | 用户给的字符串 | ✅（S3 key 就是 UTF-8 字节串） |

**都不需要转义**，这是选 S3 而不是自己造对象名方案的理由。
（fs 后端就没这么幸运——`·` 这类字符在某些文件系统上会出问题，所以 `fs/kvspace.rs` 里才有额外处理。）

**待确认 4**：前缀是否要求以 `/` 结尾？建议**要求**——否则 `s3://bucket/mo` 会匹配到 `moechat/...`。
不满足就 panic 并说清原因，不做自动补。

## 五、各原语怎么落

| `KVStore` | S3 调用 | 备注 |
| --- | --- | --- |
| `get` | `GET <key>` | 404 → `None`（**不是错误**，S3 用 404 表达「不存在」） |
| `get_many` | 并发 `GET`，或逐个 | 覆盖默认实现；先用逐个，够用再说 |
| `set` | `PUT <key>` | |
| `del` | `POST ?delete`（批量，单次 ≤1000） | 覆盖默认的逐个；分批 |
| `exists` | `HEAD <key>` | 覆盖默认的整读——**这条很值**，`HEAD` 不传 body |
| `get_part` | `GET` + `Range: bytes=off-(off+len-1)` | 原生支持 ✅ |
| `set_part` | **无原生支持** | 用默认的整读整写，见 §2.3 |
| `flush` | 列举 + 逐个删 | **危险**，见 §六 |

**没有 `scan_keys`。** 见 §五之一。

## 五之一、子树枚举：走目录索引，不用 S3 的前缀 API

需求方 2026-09-26 定：**不用 S3 的 `Prefix=` 做子树枚举，目录的子项列表单独存。**

### 为什么 `Prefix=` 本来就不对

KVSpace 的 `scan_keys(prefix)` 要的是**词边界**匹配：

```
k == prefix  或  k[prefix.len()..] 以 '/' 或 '·' 开头
```

（见原 redis 实现的过滤条件。）而 S3 的 `Prefix=` 是**裸字节前缀**——
要 `/proto` 会把 `/protocol`、`/proto2` 一起吐出来。第一版实现照搬了 `Prefix=`，
**在真桶上被 `cp_tree` 测试当场抓出来**：`del_tree` / `cp_tree` 会把同前缀不同分支的东西
一起扫进去。修法本来是客户端再筛一遍，但那是打补丁。

### 改成什么

KVSpace **本来就在每个目录 key 上维护着子项列表**（`add_child` / `read_dir_index` /
`remove_child`，存的就是那个以 `/` 结尾的目录 key）。子树枚举直接沿这份索引递归：

```
Backend::collect_subtree(base)
  ├─ 收 base 自身
  ├─ 读 base·（成员索引）与 base/（层级索引）的子项名
  └─ 对每个子项名递归
```

三个调用点（`del_tree` / `cp_tree` / `cp_list`）从 `store.scan_keys(x)` 改成 `self.collect_subtree(&x)`。

### 连带的变化

- **`KVStore` 里删掉了 `scan_keys`**。后端只需要 `get/set/del` 这类点操作，
  不必为「有没有前缀扫描能力」做适配。redis 的实现随之删除。
- **redis 也走新路径**：这是共用层，改一处两个后端同时受益。
  用 redis 的现成测试做回归，`cp_redis` / `map_coord_redis` 全过 ——
  这同时**证明了目录索引是完整的**（索引漏一项，回归就会挂）。

### 代价与前提

**前提：目录索引必须完整。** 任何绕过 `add_child` 的写入都会让 `collect_subtree` 漏 key，
在 `del_tree` 上就是丢数据。这条不变量由 cp 与 map_coord 两套语义测试在 redis 与 S3 上共同守着。
新加写路径时如果发现测试挂了，先怀疑这里。

**收益**：S3 后端不再需要 `ListObjects`，一次子树枚举的请求数与子树规模成正比但**不返回无关 key**；
索引读还天然带上了 `Backend` 已经算好的结构信息。

**错误处理不能吞。** 现有代码风格是「遇错即崩」（`panic!` 带明确信息，见 `const.rs` 里那批 `ERR_*`）。
S3 的错误要区分三类：

1. **404** → 不是错误，是「不存在」，返回 `None`
2. **HTTP 5xx / 网络超时** → 可重试，但**重试要有上限**，超了必须 panic
3. **4xx（403 签名错、404 桶不存在、400 参数错）** → **立刻 panic，不重试**。这类错误重试一万次也不会好

第 3 条尤其重要：把「签名错」当成「可重试」会让程序卡在那里，比崩掉难查得多。

## 六、`flush()` 是本设计里最危险的一个

`KVStore::flush` 的语义是**清空全部**。在 S3 上这意味着「列出并删除」——
如果前缀配错、或者实现里忘了加前缀，**会把整个桶删掉**（包括别的 kvspace 的数据）。

处置：

1. **只删 `<前缀>` 之下**，绝不碰前缀之外
2. 前缀为空（`s3://bucket`）时，`flush` **拒绝执行并 panic**，
   除非 DSN 显式带 `&allow-root-flush=1`
3. 删除走批量接口，逐批确认返回码；有失败就 panic，不静默跳过

这条不是过度谨慎：一周内已经发生过一次挂载点上的 `rm -rf` 删掉几千个远端对象的事故。

## 七、缓存层要不要

**待确认 5，本方案不做，但要说清为什么可能迟早得做。**

每次 `get` 是一次公网 HTTP 往返。腾讯云北京同区域大概是个位数毫秒，
跨地域几十毫秒。而 KVSpace 读一个逻辑值常常要读多个 key。

不做的理由：缓存带来失效、多写者一致性、内存上限三个新问题，而目前**没有实测数据说它慢**。

真要做的时候，形态应该是：**进程内、按 key、写穿（write-through）+ 有界 LRU**，
不落磁盘（落磁盘就又多一份要管的数据）。什么时候做——等有真实负载的数字。

## 八、测试

现有 `tests/` 只有 `cp.rs` 和 `map_coord.rs`，`cargo test` 依赖活的 redis（CI 里起容器）。

S3 后端的测试分两层：

| 层 | 怎么做 | 跑在哪 |
| --- | --- | --- |
| **单元** | DSN 解析、key 拼接、SigV4 签名向量（AWS 官方测试向量） | 任何地方，不需要网络 |
| **集成** | 对着真桶跑一遍 KVStore 的每个原语 | 需要凭据，**默认 `#[ignore]`**，手动跑 |

**集成测试必须能安全地重跑**：用独立前缀（如 `_test/<随机>/`），跑完清掉。
绝不能对着 `moechat/` 这种真前缀跑。

CI 不加 S3 集成测试——CI 里没有凭据，也不该把生产桶的凭据放进 CI。

## 十、凭据与安全

需求方给的凭据（`/Users/lipeng/miaobyte-1252231640/sh/腾讯云/s3/sh/rclone.sh` 里那份）
**与 50 GB 的 `miaobyte-1252231640` 桶是同一对**。

| 风险 | 处置 |
| --- | --- |
| 一对密钥开两个桶，其中一个要当 moechat 的存储底座 | **建议给 moechat 单独发一套受限密钥**（腾讯云 CAM 子账号 + 只授权 `moechat-test-1252231640`） |
| 密钥明文写在脚本里，脚本还在对象存储上 | 长期应改为环境变量 / 密钥管理服务；**本方案不把任何密钥写进仓库** |

`kvspace-durable` 是 public 仓库，**测试与文档里绝不出现真凭据**。
